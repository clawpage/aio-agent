# 个人知识库（任务知识库）设计

状态：已实现（2026-10-28，P0–P2 一次完成），决定见 §10，实现与设计的出入见 §11。参考 workspace 的 aio-db-kb（SQLite 单一事实源、唯一写入口、引用钉指纹），
但本项目必须自包含，只借鉴模型与规则，不依赖它的代码。

## 0. 一页总览

**一句话**：每个账号有一个只属于自己的「任务知识库」，由该账号的**知识管家（kb maintainer）**独自维护。
知识进库有两条路：任务做完后管家自己读任务记录提取；任务进行中执行者发现值得记或需要更正的内容，给管家发一条消息（A2A），
由管家决定怎么改。管家是唯一能写库的角色，负责去重、归领域、连成图、标来源。新任务先查这张图，几秒内拿到要点，
需要细节再顺着来源读原文。

大白话：任务目录（`workspace/tasks/<id>/`）是「档案柜」，原文都在里面；知识库是档案柜的「目录卡片 + 关系图」；
wiki 是把最常用的几十条知识直接抄成一页一页的「速查手册」。档案柜不动，卡片和手册只由管家一个人维护，
别人发现卡片写错了可以递条子，但不能自己改。

```
 ① 任务完成 ──排队──┐
                     ├─▶ 控制面邮箱 kb_packets ──▶ 知识管家（唯一写者，读任务记录与任务目录）
 ② 任务进行中 ──────┘    （提议/更正，A2A）              │ 写入内核：校验来源/领域/去重
    执行者 kb_propose                                     ▼
 沙箱 workspace/                                  控制面 per-account SQLite（事实源）
 ├─ tasks/<id>/        原文（已有）  ◀──指针+指纹── │ nodes · edges · claims · sources · revisions
 └─ kb/                投影（只读副本，可重建）  ◀──渲染── │ （执行器无法直接写到这里）
    ├─ INDEX.md        领域 → 节点 → 关系索引
    └─ wiki/<领域>/*.md 高频重要知识
                                ▲
 新任务 / 派单 / 任何内部 agent ─┴─ 读：MCP `aio_task_kb`（只读工具 + kb_propose）· skill · CLI
```

**五条规则**（从 aio-db-kb 继承，按本场景裁剪）

1. **单一事实源**：知识只在控制面的账号数据库里；`kb/` 目录是渲染出来的投影，被改了下次就覆盖，不算数。
2. **唯一写入口**：只有控制面的写入内核写库，它只接受知识管家会话的回答（一份修改单），整份校验后在一个事务里写入或整份拒绝（§11）。
   其他 agent 只能「递条子」（`kb_propose`），不能写库。
3. **没有来源不入库**：每条知识至少一条来源（任务 id + 原文位置 + 指纹，或网址 + 访问时间）；内核拒绝无来源、无领域的写入。
4. **原件不搬家，但留摘录**：任务目录可被用户或执行器改、删（不同于 workspace 的不可变 raw/），所以入库时同时保存
   一段短摘录（≤ 600 字）和原件的 sha256；原件还在就读原件，没了就读摘录并标「原件已变/已删」。
5. **账号隔离**：每个账号一个库、一个管家；member 之间、member 与 owner 之间不互通；与 owner 的家庭知识库（`aio_kb`）互不写入。

## 1. 为什么不只靠现有的三样东西

| 已有 | 是什么 | 缺什么 |
|---|---|---|
| `aio_history`（history_search/get） | 原始任务记录的全文检索（情节记忆） | 只能按关键词捞任务，结论散在长回复里；同一件事做过 5 次要读 5 遍；执行过程只留 40 步 |
| 长期约定（`agreements`） | 用户**明确说过**的规则、偏好、事实，一句话一条 | 刻意不收执行器自己学到的东西（「这个网站登录要先关弹窗」） |
| `aio_kb`（家庭知识库） | owner 维护的家庭资料 | 只给 owner 与少数成员；不收任务产物；写入要人工编译复核 |

任务知识库补的是中间这层：**从做过的任务里提炼出来、带来源、可复用的知识**（实体、事实、做法、踩过的坑），
并且有关系图，能从一个点找到相关的点。三者分工：约定 = 必须遵守的规则（每次注入，仍由 `memory_save` 记）；
任务知识库 = 按需查的经验与事实；history = 原始记录（知识库的来源之一）。

## 2. 数据模型（控制面，账号数据库内新表）

放在控制面每个账号已有的 SQLite 里（与 tasks、agreements 同库），不放沙箱：沙箱里的执行器是完整权限、不审批的，
库文件放进沙箱就挡不住它直接写。

| 表 | 作用 |
|---|---|
| `kb_nodes` | 图的点：`kind`（entity 实体 / topic 主题 / procedure 做法 / fact 事实）、`domain`、`title`、`summary`、`attrs_json`、生命周期（active / superseded / retired）、`wiki`（是否进速查手册） |
| `kb_edges` | 图的边：`src`、`dst`、`rel`（about / part_of / uses / related_to / supersedes / contradicts）、来源 |
| `kb_claims` | 挂在节点上的具体陈述（「X 网站退货要在 30 天内」）：正文、`volatility`（stable / changes，价格营业时间这类为 changes，带 `verify_after`）、`certainty`（user_said 用户说的 / observed 亲眼看到的 / inferred 推断的） |
| `kb_sources` | 来源：`task_id`、`turn`、`path`（`tasks/<id>/...` 或空）、`url`、`sha256`、`excerpt`、`captured_at`、观测状态（current / changed / missing） |
| `kb_cites` | claim/edge ↔ source 多对多 |
| `kb_domains` | 本账号的领域表（初始一组通用领域：家庭、健康、购物、出行、财务、工作、技术、账号与网站……；管家可新增，需写说明） |
| `kb_packets` | 邮箱：待管家处理的消息（任务完成提取请求、执行者提议），状态 pending / accepted / merged / rejected，附管家的处理理由 |
| `kb_revisions` | 只追加账本：每次节点/claim/边的变更一条，记由哪个 packet 引起 |
| `kb_fts` | FTS5，与 `tasks/recall.ts` 同一套切词（中文两字、拉丁按词） |

取舍（与 aio-db-kb 对照）：

- **保留**：账本 + 物化当前表、引用钉指纹、什么都不删（retired/superseded；用户主动删除除外，见 §6）、写入时校验。
- **去掉**：独立复核会话、变更集长事务、连接器/锚点解析、保鲜复核队列。理由：这是自动、高频、每账号一份的库，
  每条都做独立复核成本不可接受；信任改用 `certainty` + 来源 + `volatility` 表达，读的人自己判断要不要回原文核对。
- **只有进 wiki 才加一道检查**（§5）。

## 3. 写入：两条进库路径，一个写者

### 3.1 路径一：任务完成后，管家自己读

挂在任务转为 `completed` 的地方（`TaskService` 里 `recordFeed` 旁边），只往邮箱放一条「请提取任务 X」，不阻塞。默认跳过：
普通聊天/直接回答（没建任务目录、没有工具调用）、每日推送和定时任务的例行运行、失败/中断/unknown 的任务、
用户标了「别记这个」的任务。补充追加到原任务后再次完成时，只提取上次之后新增的轮次。

管家读的材料：`history_get(id, process=true)`（原话与补充、最终结果、每步一行的执行过程）、任务目录 `tasks/<id>/` 里的文件、
该任务在执行中已经发过的提议（路径二，避免重复）。可以一批处理多个任务。

已知盲区：执行过程只记「调用了什么」不记「看到了什么」，且最多 40 步；过程中看到的原文、报错、取舍理由，
如果没进最终回复或文件，管家看不到。这部分由路径二补。

### 3.2 路径二：任务进行中，执行者给管家递条子（A2A）

所有本账号的任务 agent（执行器、它的子代理）都有 `kb_propose`，在**做任务的当下**把消息发给管家：

| 类型 | 什么时候用 | 例子 |
|---|---|---|
| `add` | 发现值得以后复用的事实、做法、踩坑 | 「Costco 网站结账前要先选取货门店，否则运费显示为 0 是假的」 |
| `correct` | 查到的知识库内容和现在看到的不一致 | 节点 X 的营业时间已改为 9–18 点，附页面网址 |
| `outdated` | 内容过时、链接失效、流程变了 | 「Y 网站登录已改为验证码，原做法不再适用」 |
| `wrong` | 用户当场纠正了知识库里的说法 | 「用户说 Roy 现在不再对鸡蛋过敏」（同时用 `memory_save` 改约定） |

- 每条提议必须带：目标（新内容，或要改的节点/claim id）、理由、证据（本任务里的文件路径、网址、或「本任务第 N 轮用户原话」）。
  证据由内核按本任务定位并计算指纹，执行者不能编。
- 这是异步消息：发出即返回提议 id，执行者继续做自己的任务，不等管家；当前任务直接用它自己看到的新信息。
- **先挂旗、后修改**：`correct` / `outdated` / `wrong` 一到邮箱，被指向的节点立刻在读接口上显示「有待处理的更正（来自任务 X，理由…）」，
  别的任务在管家处理前读到它也不会盲信旧内容；这一步是控制面代码做的，不经模型、不改知识本身。
- 管家处理后在 `kb_packets` 写结论（accepted / merged / rejected + 理由）；发出提议的任务若还在进行，可用 `kb_propose_status` 查结论。
- 防滥用：每个任务提议数和单条长度有上限；同一任务对同一节点的重复提议合并；纯闲聊、一次性细节、密码证件号等由内核与管家拒收。
- 执行策略（skill 与提示词）里写清楚：常规结论不必提议，任务结束后管家会读；只有「记录里看不出来」的东西（过程中看到的原文、踩坑）
  和「知识库已经错了」才提议。

**为什么经邮箱而不是直接对话**：执行者和管家不一定同时在线（管家是批处理角色，§3.3）；控制面要能审计、限流、重放，失败不丢；
「先挂旗」需要控制面在消息到达那一刻就知道。消息是有 schema 的 JSON（版本号随 `src/common/version.ts` 管理），形状参照 A2A 的
task/message/parts（来源 agent、任务 id、内容、证据），以后要接标准 A2A 只是加一层适配。

### 3.3 知识管家（唯一写者）

「管家」是一个**角色**，不是一个永远开着的会话：

- 每个账号同一时刻最多一个管家在跑（控制面租约），处理邮箱里排队的消息，一批处理完就结束。
  它的「记忆」就是库本身，每次开工先读图，不靠越来越长的会话历史（长会话会被压缩、丢细节，也越跑越贵）。
- 处理顺序：更正类提议（`wrong` > `correct` > `outdated`）优先，其次执行者的 `add`，最后任务完成提取。
  有更正类提议时尽快开一批（如 1 分钟内），其余攒批（如 10 分钟或 5 条）。
- 没有写工具（§11）：管家与所有 agent 拿到同一个只读 + `kb_propose` 的服务，最后回答一份 JSON 修改单
  （`domain` / `node` / `update_node` / `claim` / `link` / `merge` / `retire` / `wiki` 与每条消息的处理结论），由控制面从它自己发起的会话里收下。
- 管家做三件执行者做不了的事：**去重合并**（同一个人/商品/网站已有节点就挂上去）、**冲突处理**（新旧说法矛盾时用
  `supersedes` 或 `contradicts` 连起来并保留两边来源，不默默覆盖）、**领域归类**（用本账号领域表，必要时新增）。
  处理更正时要读提议附的证据，证据不足就 rejected 并写理由，不能照单全收。
- 写入内核（控制面 TS 代码，不是模型）兜底：来源必须存在且路径在本账号工作区内、指纹在入库时由内核计算（管家不能编）、
  领域必须在表里、claim 正文长度上限、敏感模式（证件号、卡号、密码字样）直接拒收。
- 跑在本账号自己的沙箱里（能读 `tasks/<id>/` 原文核对）。**所有账号的管家统一用 `gpt-6.1-sol`、low 推理强度**（已定，2026-10-28）。
  成员本来就统一是 `gpt-6.1-sol`，成员模型网关允许请求 low，管家请求 low 即可，网关不用改；owner 的管家同样固定为 Codex 会话，不跟随 owner 执行器的选择（Claude Code）。

## 4. 读：新任务怎么用

1. **派单时自动带一点**：派单已有召回（`recall.ts`）；新增按本次消息查 `kb_fts`，取最相关的 ≤ 5 个节点的标题 + 一句摘要 +
   一跳邻居（有待处理更正的节点带旗），注入执行会话开头（与「长期约定」同样带内容版本号、续接时去重），约 800 字上限。
2. **按需深查**（只读工具，所有本账号内部 agent 都有）：
   - `kb_search(query, domain?, kind?)` — 相关度排序的节点与 claim，带片段；
   - `kb_get(id)` — 节点全文：claims、来源列表、`certainty`、需不需要重新核实、待处理更正；
   - `kb_neighbors(id, rel?, depth≤2)` — 顺着图走；
   - `kb_source(source_id)` — 原文：原件还在且指纹一致读原件片段，变了/没了读入库时的摘录并注明。
3. **文件方式**：`workspace/kb/INDEX.md` 与 `wiki/` 让不调工具、只会 `grep`/读文件的场景（终端、Jupyter、子代理）也能用。
   投影在每次提交后由控制面重新渲染写入沙箱（沙箱醒着时写，睡着时下次唤醒补写），文件头注明「生成文件，改了会被覆盖；
   要改请用 kb_propose」。

**接口形态**：核心是控制面的一组函数 + HTTP 路由；对外三种包装共用它：

| 形态 | 给谁 | 说明 |
|---|---|---|
| MCP `aio_task_kb` | Codex / Claude Code 执行器 | 推荐默认：与 `aio_history` 同一网关模式，按运行时令牌限定账号与读/写 |
| skill（seed 进沙箱） | 所有执行器 | 写「什么时候查、怎么判断可信、什么时候回原文、什么时候递条子」，替代把长策略塞进每次提示词 |
| CLI `aio-kb`（沙箱内） | 终端、脚本、子代理 | 薄壳，带本运行时令牌调同一 HTTP 路由；读 + `propose` |

不建议让 CLI 直接读库文件：库在控制面，沙箱碰不到，这正是「只有管家能写」能成立的前提。

## 5. wiki：高频重要知识的速查页

- 候选：被新任务读到/引用次数高（记录 `kb_get` 与派单注入命中）、`certainty` 不是 inferred、有 ≥ 2 个独立任务来源的节点。
- 管家在修改单里写 `wiki` 项，写一页 Markdown（结论在前、来源编号在后）；**进 wiki 前由另一个会话做一次核对**
  （读来源原文确认页面每句话有依据），通过才渲染进 `kb/wiki/`。这是本设计里唯一保留的独立复核，因为 wiki 会被不加怀疑地直接读。
- wiki 页对应的节点收到更正类提议时，页面立即带上「有待处理的更正」横幅，管家处理后重新核对再渲染。
- 每账号 wiki 页数上限（如 50），超出按热度淘汰回普通节点；`volatility=changes` 的内容不进 wiki 正文，只留「去哪查」。

## 6. 隐私、权限与删除

- 读与提议：只在本账号内；owner 不能经此读 member 的库（与任务隔离一致）。
- 写：只有控制面内核，从本账号管家会话的回答写入；沙箱里不存在任何写入凭据。
- 用户可见可控：配置页（或工作区新应用）「知识库」：按领域浏览图、看每条的来源、删除一条或一个领域、整体开关；
  删除 = 物理删除该行与摘录并记账本（「被谁删了」），不是标 retired——这是用户的数据，应能真正忘掉。
- 账号删除时连库一起删。导出：整账号数据导出里包含它。

## 7. 与 aio-db-kb 的关系

**二者并行存在，暂不打通（已定，2026-10-28）**：

| | 个人知识库（本设计） | 家庭知识库（aio-db-kb，`aio_kb`） |
|---|---|---|
| 归属 | 每个账号一份，只属于这个人 | owner 与 cr 共享的家庭信息 |
| 来源 | 本账号做过的任务 | raw/ 原始资料与 owner 的项目 |
| 写者 | 本账号的知识管家 | aio-db-kb 写入内核（编译、复核），执行器只能 `kb_note` |
| 信任 | 来源标注 + `certainty` | 独立复核 |

不互相写、不互相同步。执行器两个都能读（家庭知识库仍只给获准账号）时，各按各的策略用：家庭成员的资料、病历、证件类事实
以家庭知识库为准；个人知识库里与之冲突的内容，执行者用 `kb_propose(correct)` 提给自己的管家，不去改家庭知识库。
以后若要打通，只考虑单向：个人库的 `user_said` 家庭类 claim 作为候选笔记经 `kb_note` 进 raw/aio-notes/，仍由 aio-db-kb 自己收录。

## 8. 运行与成本

- 管家作业走独立队列，每账号同时最多 1 个，不占用户的并行名额（`PA_MAX_CONCURRENT_TURNS`），用户有新任务时让路。
- 依赖沙箱醒着：管家只在容器醒着时跑，不为整理知识唤醒或拖住沙箱，不影响空闲休眠的判定；邮箱在控制面，沙箱睡着时消息照样排队，
  「先挂旗」也照样生效。
- 读任务记录而不是派生线程，单次成本是一份精简记录；多任务一批处理再摊薄。不采用 fork：它要把整个任务线程重发一遍，
  且 Codex 与 Claude Code 之间不能互相派生；记录里缺的细节由路径二按需补。
- member 共用控制面 ChatGPT 登录，已经会遇到 429：管家作业使用低优先级，遇限流直接推迟到下一批，不与用户任务抢重试。
- 用量照常计入本账号（模型固定为 `gpt-6.1-sol` low，见 §3.3），用量页暂不单列（§11）。

## 9. 分阶段

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | 表结构 + 写入内核 + 读/提议工具（MCP）+ 投影渲染 | 内核单测（无来源/越界路径/敏感内容/非管家写入被拒）；人工抽 30 条看来源是否真能回到原文 |

任务回合数与耗时，而不是数入库条数。

## 10. 已定事项（2026-10-28）

1. 进库方式：任务完成后管家读任务记录提取；执行中由任务 agent 用 `kb_propose` 发给管家（§3）。不用 fork。
2. 覆盖范围：所有账号；只有 owner 回溯最近 14 天，member 从新任务开始（§9）。
3. 管家模型：所有账号统一 `gpt-6.1-sol` low（§3.3）。
4. 用户可见度：任务结果里不提示记了什么；只在知识库页面（P2）里可见、可删。
5. 与家庭知识库：并行存在，暂不打通（§7）。

## 11. 实现与设计的出入（2026-10-28）

1. **没有写模式 MCP 地址**。原设计让管家的运行时令牌带写工具。但 Codex 只放行策略文件（沙箱里的 `requirements.toml`）列出的 MCP 地址，
   写地址要被放行就得写进沙箱；沙箱里的执行器权限完整，读得到它，「只有管家能写」就不成立。改为：管家会话只读，回答一份修改单，
   控制面从它自己发起的一次性会话事件流里取回答，内核校验后写入。沙箱里任何地方都没有写入凭据。
2. **校验比设计更严**：除来源存在、路径在任务目录内、指纹由内核计算外，引用的原话必须逐字出现在原文里（文件，或任务的消息、结果、工具输出），
   网址必须是该任务打开过或提到过的。管家编不出不存在的依据。
3. **管家读到的材料比 `history_get` 多**：直接从事件表取每步的工具输出（截断），而不是只有每步一行的摘要，部分补回了「看到了什么」的盲区。
4. **用量不单列**：管家会话的 token 照常计入账号（与派单、起名一样按会话记账），用量页暂不单列「知识整理」。
5. **页面在独立的「知识库」页**（`/knowledge`），所有账号可见；多了一个整体开关。
6. **管家不用 MCP 工具**（上线首批发现）：一次性只读会话在审批 never 下，MCP 工具调用会被自动拒绝，首批 4 个任务因「无法核对已有节点」全被拒。
   改为控制面按每条消息先检索最相关的已有节点（最多 20 个，含 id、陈述与关系）放进材料，管家不再调用工具；被误拒的消息重新排队。
