# 共享知识库设计

状态：设计已定（2026-10-31），按 §9 分期实现。个人库的原有设计见 [TASK-KB.md](TASK-KB.md)，本文只写共享库新增与改变的部分。

## 0. 一页总览

**一句话**：每个账号自带一个**个人库**，还能建立或加入任意多个**共享库**；家庭、项目都只是共享库的用法，代码里没有「家庭」「项目」之分。
所有库共用一套机制（条目、写入内核、读工具、管家）；共享库另有成员、可改的写入规则、可回滚的修改记录。

```
任务完成 → 本人的个人管家（读得到任务原文）
             │ 对照本人所在各共享库的规则（第一道判断）
             ├─ 只属于自己 ───────────────▶ 个人库（账号数据库）
             └─ 符合某库规则 → share ──▶ 该共享库邮箱（摘录、指纹、贡献者）
                                                │
执行器 kb_propose（目标在共享库、或点名库名）────┤
成员在页面上直接编辑 ─────────────────────────┐  │
                                              ▼  ▼
                                   共享库管家（第二道判断，控制面直接调模型）
                                              │ 写入内核：校验 → 一个事务写入
                                              ▼
                              data/kbs/<库 id>.sqlite（条目 + 规则 + 修改记录）
```

**规则**

1. 每个库只有一个写者：个人库是本人的管家，共享库是该库的管家；人在页面上的编辑同样经写入内核。
2. 共享库只存摘录，不存原件。原任务只有本人看得到，别人看到的是摘录和「来自谁」。
3. 进共享库要过两道判断：本人的个人管家判断「这条可以分享」（拿不准不分享），共享库管家按库规则判断「这库要不要」。
4. 共享库的每次改动都记录改前改后，可以按条目、按一次改动、按规则版本回滚；回滚本身也是一次改动。
5. 每次读写都由控制面核对成员身份；执行器仍只用自己账号的令牌。

## 1. 库

| | 个人库 | 共享库 |
|---|---|---|
| 成员 | 本人，账号自带 | 多人，经邀请链接加入；一个人可加入任意多个 |
| 存放 | 账号数据库（不迁移） | `data/kbs/<id>.sqlite`，主库只记库与成员名单 |
| 写入规则 | 个人管家的提取策略 | 建库时从预设（家庭 / 项目 / 空白）挑一段起步，之后任何成员可改，留版本 |
| 来源 | 任务（原文可读） | 任务摘录（来自谁）、成员手写、网址 |
| 删除 | 物理删除，真正忘掉（TASK-KB §6） | 删除也是一次可回滚的改动；解散库时整库文件删除 |
| 速查页（wiki） | 有 | 第一版没有 |

**代码里的统一**：库就是「数据库 + 库 id」。`kb_*` 表、写入内核（`applyKbAnswer`）、读函数（`searchKb` / `getKbNode` / `kbNeighbors` / `listKb`）都按 `(db, id)` 工作：
个人库是 `(账号库, 账号 id)`，共享库是 `(库文件, 库 id)`。不同的只是「来源怎么核对」：个人库核对任务原文，共享库核对邮件里已经核对过的摘录或成员手写，由内核的 `verify` 参数决定。

## 2. 数据

### 2.1 主库（owner 运行时的数据库）

| 表 | 作用 |
|---|---|
| `kb_libraries` | `id`（`kbl_…`）、`name`、`admin_id`、`created_by`、`created_at` |
| `kb_library_members` | `library_id`、`user_id`、`joined_at` |
| `kb_library_invites` | `id`、`library_id`、`token_hash`（只存哈希）、`created_by`、`created_at`、`expires_at`、`revoked_at`、`uses` |

### 2.2 共享库文件

- 与个人库相同的 `kb_*` 表（同一份建表语句，`owner_id` 填库 id）。
- `kb_sources` 多两列：`kind`（`task` / `manual` / `url`）与 `contributor`（账号 id）。个人库也加这两列，原有行为 `task`。
- `kb_rules`：规则的每个版本（`version`、`text`、`by`、`at`、`restored_from`）。
- `kb_changes`：每次改动一行（`id`、`by`、`kind`：`maintainer` / `edit` / `undo` / `restore`、`summary`、`at`、`undoes`）。
- `kb_change_rows`：这次改动里每一行的改前与改后（`tbl`、`pk`、`before_json`、`after_json`）。
  由库文件里的触发器在 `kb_nodes`、`kb_claims`、`kb_edges`、`kb_sources`、`kb_cites`、`kb_domains` 的增删改时自动写入，
  只在一次改动打开时（`kb_change_cursor` 有值）记录，所以任何写入路径都不会漏记。改动在写入事务里打开、在提交前关闭。

## 3. 写入

### 3.1 第一道：个人管家

账号属于某些共享库时，个人管家的材料里多一节「你所在的共享库及其规则」，修改单里多一种操作：

```
{"op":"share","library":"<库 id>","title":"<主题>","text":"<要分享的一条陈述>","sources":[<和 claim 一样的任务来源>]}
```

内核像核对 claim 一样核对来源（任务原文里逐字存在、敏感内容拒收），并确认该账号是这个库的成员；
个人库的事务提交后，再把它作为邮件放进共享库邮箱（带摘录、指纹、贡献者、来源任务 id）。
提示词要求：只分享符合该库规则、对其他成员也有用的内容；拿不准就不分享；分享的内容通常也照常记进个人库。

### 3.2 执行中：kb_propose

- 目标条目在共享库：证据先按本任务核对，再把摘录随邮件进该库邮箱；更正类立刻给条目挂旗。
- `library` 参数（库名）点名写入：按库名匹配本人所在的库；匹配不上或有多个时返回错误，执行器改为写进个人库并告诉用户。

### 3.3 第二道：共享库管家

- 不需要沙箱：控制面直接调用模型（`gpt-6.1-sol`、low，经控制面自己的 ChatGPT 登录），用量记在这一批邮件的贡献者账上（一批只处理同一贡献者的邮件）。
- 材料：本库规则、领域表、与这批邮件最相关的已有条目（最多 20 个）、每封邮件（陈述、贡献者、已核对的摘录）。
- 回答与个人管家同一格式的修改单（不含 wiki）。来源写 `{"packet":"<邮件 id>","quote":"<该邮件摘录里的原话>"}`，
  内核核对原话确实在那封邮件的摘录里，再把摘录、指纹、贡献者、来源任务 id 写进 `kb_sources`。
- 有更正类邮件时 1 分钟内开一批，其余 2 分钟攒一批；失败三次的邮件标 `failed`。
- 每一批是一次改动（`kind=maintainer`），可以整批撤销。

### 3.4 人直接编辑

成员在页面上：新建条目（标题、领域、类型、摘要、若干陈述）、改标题 / 摘要 / 领域、增改删陈述、删除条目。
陈述的来源记为 `manual`（某某手写）。同样经写入内核：长度上限、敏感内容拒收。每次保存是一次改动（`kind=edit`）。

## 4. 回滚

| 粒度 | 做法 |
|---|---|
| 一次改动 | 按改动里的行倒序恢复改前状态。若其中某行之后又被改过（当前状态 ≠ 改后），拒绝并列出冲突，先撤销更晚的改动 |
| 单个条目 | 「恢复到某次改动之后的样子」：把这次之后、涉及该条目（条目本身、它的陈述、关系、引用）的行逐个倒序恢复 |
| 规则 | 选一个旧版本恢复，等于新存一个内容相同的版本（记 `restored_from`） |

回滚本身也是改动（`undo` / `restore`），出现在历史里，可以再撤销。

## 5. 成员与邀请

- 建库的人是管理员，可以转让。只有管理员能解散库、移出成员；其余操作（编辑、改规则、生成或作废邀请链接、回滚）所有成员平等。
- 邀请链接 `https://<主站>/knowledge?join=<令牌>`：任何成员可生成，默认 7 天有效、可多人使用，可随时作废。令牌只存哈希。
  打开链接后页面显示「某某邀请你加入「库名」」，点「加入」即加入。已是成员时直接打开该库。
- 退出：立刻失去访问；写过的条目留在库里，署名保留。管理员退出前须先转让（只剩自己时，退出等于解散）。
- 解散：删除库文件与名单，不能恢复。

## 6. 读

- `kb_search`：个人库与本人所在的全部共享库一起搜，每条结果标出处（`library`：库名，个人库为 `personal`）。
- `kb_get` / `kb_neighbors`：按条目 id 在本人能读的库里找。共享库条目的来源带贡献者名。
- `kb_source`：共享库来源只返回摘录、贡献者与时间，不读原件（原件在别人的沙箱）。
- `kb_libraries`：列出本人所在的共享库与各自规则，供执行器判断点名写入。
- 派单时的自动注入同样合并共享库的命中，标出处。个人库的总开关关闭时不注入任何库。

## 7. 页面

「知识库」页顶部切换「个人 / 各共享库 / ＋新建共享库」。共享库下四块：

- **条目**：同个人库的浏览，另有新建、编辑、删除；条目详情里有「历史」，可恢复到某次改动之后的样子。
- **规则**：当前规则（可编辑）与版本历史（可恢复）。
- **成员**：成员列表、管理员操作（移出、转让、解散）、邀请链接（生成、复制、作废）、退出。
- **历史**：改动列表（谁、什么时候、做了什么、涉及几处），可撤销。

## 8. 与现有系统

- 个人库的数据与行为不变（物理删除、速查页、整体开关），只是代码走统一接口。
- `aio_kb`（owner 与 cr 共用的家庭知识库，来自原件、独立复核）保持并行、暂不打通；新共享库管日常知识，`aio_kb` 管原件类资料。
